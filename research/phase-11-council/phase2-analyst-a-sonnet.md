### I-01: Tell a replay from a repeat (`OBSERVED`)
- **Technically meaningful:** Yes. It separates two situations the current code conflates — "a different model re-asked the same question after a crash" and "the model deliberately repeated a command after seeing its result" — using a state the ledger already has a slot for.
- **Real problem? (evidence, tagged):** VERIFIED — I independently reproduced the structural claim: `agentctl/kernel/ledger/store.py:349-350` defines `observed()`, and `grep -rn "\.observed\(" agentctl/` returns only that definition, zero call sites. VERIFIED — `agentctl/kernel/gate.py:67-117` shows the aliasing and SUBSTITUTE/BLOCK paths exactly as cited. INFERRED — the architect's "P1" reproduction (edit→test→re-run producing SUBSTITUTE-with-stale-output or BLOCK) is a straightforward reading of `_decide_on` (gate.py:93-117) plus `record_tool_error` (gate.py:282-315): a non-replay-safe tool that fails is BLOCKED outright, and a repeated identical call after COMMITTED returns the old `observation` via SUBSTITUTE. I did not re-run P1 myself (out of scope to write new scratch scripts beyond what's needed to verify), but the code path supports it exactly as described.
- **Established patterns / prior art (links, tagged):** This is closest to "effects-once" / outbox-pattern deduplication in distributed systems, and to Stripe's idempotency-key model (VERIFIED, https://docs.stripe.com — "If the first request succeeded, the API skips making new changes and returns an updated response"). The distinction the architect draws (a call the caller has *seen the result of* is not ambiguous) is standard practice in exactly-once messaging (e.g., Kafka's "read-process-write" idempotent consumer pattern), though I found no single canonical paper for this specific shape — INFERRED from general distributed-systems practice, no source found for a direct match.
- **Why useful:** It removes a source of false human interventions that the architect correctly notes would otherwise contaminate every later experiment (I-03, I-04, I-20, I-27 all measure "false BLOCK" as a metric).
- **Evidence to proceed:** The zero-caller confirmation on `observed()` is itself strong evidence: a state was designed and wired into the transition table (`models.py:71-83`, `COMMITTED -> OBSERVED` is legal) and never used. That is a completed-but-disconnected feature, not a hypothetical.
- **Questionable assumptions (including any wrong citations):** I found one thing worth flagging, not a wrong citation but a data-quality note the architect handled correctly: `docs/0041` §1's table says "11 EXECUTE, 1 BLOCK" but the very next paragraph says "the **two** blocked effects were failed bash commands" — 11+1=12 versus the stated 14 total effects, and "two" versus "1 BLOCK" is an internal inconsistency in `0041` itself. The architect flagged this data as "a hypothesis to confirm, since the 0041 ledger is not in the tree" rather than asserting it, which was the right call — I confirm there is no ledger artifact from that run checked into the repository to resolve the discrepancy.
- **Grounds to reject:** Per the architect's own falsification: if OpenHands persists an event and fires the SDK callback in an order where a crash between them leaves OBSERVED written but the ledger's own durability guarantee (`store.py`'s `synchronous=FULL` docstring, "a write returns only when it is durable") broken, then OBSERVED is unsound. This is a real risk worth testing, not just a formality — Seam B's `_close` (cited at `seam_b.py:191-210`) is exactly the kind of place where "the model saw it" and "the ledger recorded it" could desync under a crash.
- **Validating experiment:** The architect's design (local chaos suite + a live "fails then passes" task) is good. I would add one thing: a chaos-suite test that kills the process *between* `_close`'s ledger write and its return to the SDK, specifically targeting the OBSERVED transition, since that is the new failure surface this idea introduces and the existing nine-point suite was not designed around it.
- **Already covered? (path:line):** No. `agentctl/kernel/ledger/models.py:65,77` defines the state and transition; `agentctl/kernel/ledger/store.py:349-350` defines `observed()`; zero callers anywhere in `agentctl/`, confirmed by direct grep.
- **Verdict: PURSUE** — a small, local, well-scoped correctness fix with a state machine already built for it, verified independently to be dormant, and directly upstream of every experiment that will measure "false interventions."

## Cross-cutting findings

**1. The OpenRouter "governed globally" sentence is the single most consequential fact this review surfaced, and the Architect's document does not mention it.** I fetched `openrouter.ai/docs/api-reference/limits` directly and found, at the top of the page, above the per-key `free_model_daily_requests` mechanism the project already relies on: *"Making additional accounts or API keys will not affect your rate limits, as we govern capacity globally."* The project's entire multi-account design (`docs/0033`'s title is literally "The account is the unit, not the provider"; `docs/0038` §9.4's "6 × 50 = 300/day"; `docs/0040`'s whole arithmetic) rests on OpenRouter's free-model daily cap being independent per account. I could not resolve the contradiction from the documentation alone — it most plausibly refers to a *different* limit (per-model/provider capacity throttling and DDoS protection, described two sections later on the same page) rather than the free-model daily cap, but the page does not say so explicitly, and I would not want the council to treat "6×50=300" as settled without the cheap, direct test named under I-13: burn one account's quota and check whether a sibling account's `remaining` count moves.
