### I-01: Tell a replay from a repeat (`OBSERVED`)
- **Technically meaningful:** Yes. It separates two distinct events the current code conflates — "this exact call was already committed and nobody has seen the result" vs. "the model saw the result and is calling again on purpose." That is a real state-machine gap, not a cosmetic one.
- **Real problem? (evidence, tagged):** VERIFIED — I read `agentctl/kernel/gate.py:63-117` and `agentctl/kernel/ledger/store.py:349-350` myself. `find_by_intent` aliasing has no state filter (`gate.py:72-77`), `_decide_on` substitutes for both `COMMITTED` and `OBSERVED` (`gate.py:99-102`), and `store.observed()` (`store.py:349-350`) has **zero callers anywhere in `agentctl/`** — I grepped `agentctl/` for `\.observed\(` and found no matches outside the store's own definition. `record_tool_error` (`gate.py:282-315`) blocks every non-replay-safe failure regardless of whether the model already saw it. This is a confirmed, reproducible defect, not a hypothesis.
- **Established patterns / prior art (links, tagged):** Temporal's durable-execution model treats "activity already executed" and "result already delivered to caller" as related but distinct facts, and documents that activities must be idempotent precisely because a worker can crash between execution and delivery (UNVERIFIED, from Temporal's own blog, no single canonical URL fetched verbatim — treat as background pattern-matching, not a citation). More directly on point: this is the same distinction between "at-least-once execution" and "exactly-once delivery" that any WAL-based system with a client ACK step draws. No single external source is required to validate this — it follows from the state machine already in the code.
- **Why useful:** It sits directly in the owner's stated gap ("the real work the harness performs") — the edit → test → re-run loop is the most common coding-agent action, and it is currently mishandled. Fixing it removes a source of false human interventions that would otherwise contaminate every later before/after experiment (I-03, I-04, I-27).
- **Evidence to proceed:** P1's reproduction is plausible and matches the code path exactly as I read it (BLOCK via `record_tool_error`, SUBSTITUTE via intent-hash alias to a `COMMITTED` twin). `docs/0041` §1's "2 blocked failed bash commands" is consistent with, but does not prove, this being the cause — the Architect is honest that this is a hypothesis, not a confirmed match.
- **Questionable assumptions (including any wrong citations):** I checked every `path:line` cited in this entry against HEAD and found none wrong. The one soft spot is the risk the Architect already names: OpenHands' event-persistence-vs-callback ordering has to actually guarantee "OBSERVED implies the model has the bytes" — if a crash can land between `_close()` firing and the observation truly reaching the model's context, OBSERVED would be marking things that a resume could still lose. That has to be proven by the chaos suite, not assumed.
- **Grounds to reject:** None found. Rejecting would require either that the ordering guarantee above fails under chaos testing, or that live agents almost never re-issue byte-identical non-replay-safe commands (unlikely given how models handle test-driven loops).
- **Validating experiment:** The Architect's plan is good. I would add one thing: assert *specifically* that a crash injected between Seam B's `record_success_by_id`/`record_tool_error` write and the SDK's own event persistence still produces at most one COMMITTED/OBSERVED transition — i.e., add this exact interleaving as a tenth chaos point rather than trusting the existing nine to cover it, since none of the nine points in `docs/0012` §6 were designed around this new state.
- **Already covered? (path:line):** No. `EffectState.OBSERVED` is declared (`agentctl/kernel/ledger/models.py:65`) and its only legal transition is `COMMITTED -> OBSERVED` (`models.py:77`), but nothing writes it. Confirmed not implemented.
- **Verdict: PURSUE** — this is a real, independently-confirmed correctness gap with a small, kernel-local, zero-quota-testable fix that sits on the critical path of the most common agent action. It should land before any live experiment that measures human interventions or false blocks, exactly as the Architect's own priority order (§D.1) argues.

### I-02: One driver per conversation, enforced
- **Technically meaningful:** Yes. Lease-based mutual exclusion with fencing tokens is a well-understood distributed-systems pattern (the classic reference is Martin Kleppmann's "How to do distributed locking" critique of naive leases, UNVERIFIED from memory, no URL fetched — flagging rather than citing). The point of a fence token is precisely that a *live* re-check on every write is what makes takeover safe; a fence checked only when a prior record exists is a known-shape hole in that pattern (it protects existing state but not fresh writes).
- **Real problem? (evidence, tagged):** VERIFIED — I read `agentctl/kernel/ledger/store.py` myself. `renew()` (`store.py:135-140`) exists and is never called anywhere in `agentctl/` (grepped for `\.renew\(` — zero hits outside the definition and its own docstring). `write_intent` (`store.py:277-304`) only calls `_assert_fence` "if prev is not None" (`store.py:283-284`), exactly as claimed — a brand-new `tool_call_id` from a superseded holder is never fence-checked. `agentctl/runtime/runner.py:212` reads `takeover=bool(resume)` verbatim, confirmed by direct read.
- **Established patterns / prior art (links, tagged):** UNVERIFIED (no URL fetched) but well-established: fencing tokens are the standard fix for "the crashed process isn't really dead" in distributed leader election (ZooKeeper recipes, Chubby). The project already implements the token half of the pattern; it has simply left the second half (fresh writes) unguarded and the first half (renewal) unused, which is a partial implementation rather than a novel gap.
- **Why useful:** The project states this exact invariant is what decides multi-agent "at any budget" (`docs/0038` §10.3, which I re-read). If the enforcement of the *single*-agent case is this weak, the argument that multi-agent is unsafe rests on a foundation that is itself unproven under the concrete scenario of two `--resume` invocations.
- **Evidence to proceed:** P2's reproduction (fresh id passes the zombie guard) is a direct, mechanical consequence of the code I read — this is not speculative.
- **Questionable assumptions (including any wrong citations):** Citations check out. One assumption worth stating explicitly: renewing the lease "on every gate decision" (as proposed) adds a synchronous SQLite UPDATE to the hot path of every tool call. Given `synchronous=FULL` is already deliberate there (`store.py:1-8`), this is probably negligible next to LLM latency, but it should be measured by I-03 rather than assumed away.
- **Grounds to reject:** Only if OpenHands' own conversation persistence already prevents two processes from resuming one conversation id (e.g., a file lock on the persistence directory) — the Architect names this as the falsification condition, and it is the right one. I did not find evidence either way in `runner.py`'s `Conversation(...)` construction; it is worth a quick source check before writing the fix, since if OpenHands already serializes this, the fix becomes defense-in-depth rather than a live hole.
- **Validating experiment:** Sound as described. I would add: verify the theoretical hole first with a *local* experiment before touching runner.py — write a two-line pytest that calls `store.acquire()` twice from different `holder` values with `takeover=True` and asserts the first holder's fresh `write_intent` after the takeover is *not* fenced today (this is literally P2, formalized as a permanent regression test rather than a one-off scratch script).
- **Already covered? (path:line):** No. Confirmed absent: no caller of `LedgerStore.renew` in `agentctl/`, and `_assert_fence` is conditionally skipped exactly as described (`store.py:263-276`, `283-284`).
- **Verdict: PURSUE** — independently confirmed, small, kernel-only, zero-quota to test, and it protects the correctness argument the project leans on hardest for its multi-agent SKIP decision.

### I-06: Approvals that do not stop the run
- **Technically meaningful:** Yes — converting a blocking `input()` call into a durable ledger state with an async resolution path is the standard fix for "human-in-the-loop that can't be in the loop right now," and the project already has the storage primitive (`BLOCKED` state, `resolve --retry`) to hang it on.

No paper is needed to justify the pattern; it is standard operational practice for long-running automated systems with irreversible steps.

- **Already covered? (path:line):** No. Confirmed: `_install_confirmation` (`runner.py:290-338`) has no non-interactive branch, and no `pending_approval` marker or `agentctl approve` command exists (`agentctl/cli.py` has `resolve` and `blocked` only — confirmed by reading the full argparse setup).
- **Verdict: PURSUE** — small, reuses existing durable state, directly closes a real "blocks forever / silently refuses" defect that sits squarely in the owner's "real work" gap.

- **Evidence to proceed:** Strong — the mechanism is built and unit-tested against a mock, the tool that would exercise it against a real model does not exist, and the fake-service design (a local stdlib HTTP server honoring `Idempotency-Key`) is a cheap, safe way to close that gap without touching a real payments API.
- **Questionable assumptions (including any wrong citations):** No wrong citations found. The Architect's own named risk — that a real model might fill the `idempotency_key` argument itself with a fresh, unstable value on a resumed call, since Seam C deliberately leaves a caller-supplied key alone (confirmed: `seam_c.py`'s `_stamp_idempotency_key` explicitly checks `if existing: return action` — a model-supplied key is never overwritten) — is, in my independent judgment, a real and non-trivial risk: nothing in the tool schema (as proposed) would obviously stop a model from inventing a key, and no mock has ever tested what a real model actually does with an idempotency-key-shaped argument it's asked to fill in.
- **Grounds to reject:** None found for the mechanism itself. Would reject scope creep toward a broader HTTP-tool feature (general internet access) — the Architect's own mitigation (localhost-only by default, with an allowlist) is the right and necessary constraint, and should be enforced by a test, not just a default.
- **Validating experiment:** Sound as designed. I would add the model-supplied-key risk as a specifically labeled fourth cell in the experiment matrix (compliant server / non-compliant server / crash / no-crash is already 2×2=4 cells at n=3 tasks each = 12 runs; I would add one more arm specifically prompting the model in a way likely to elicit it supplying its own key, e.g. a system/task framing that mentions idempotency explicitly, to deliberately try to trigger the named risk rather than hope it shows up incidentally).
- **Already covered? (path:line):** No. Confirmed: the mechanism exists (`seam_c.py`) and is unit-tested, but no real HTTP tool, no fake service, and no live-model test of this path exist anywhere in the tree.
- **Verdict: PURSUE** — this is the project's own highest-stakes untested correctness mechanism, the design matches industry-standard idempotency-key practice (independently corroborated against Stripe's own documented approach), and the fake-service design makes testing it against a real model cheap and safe.

## Important things the Architect missed

- **The `session_affinity` wiring gap for I-12** (documented above under I-12's "Questionable assumptions") — litellm's proxy does not automatically map the SDK's `x-litellm-session-id` header into the `metadata.session_id` field that `DeploymentAffinityCheck` actually reads. This is a small fix, but the Architect's write-up frames arm (B) as pure configuration, and it is configuration plus a few lines in `agentctl`'s own hook.
- **The per-retry-attempt granularity of litellm's failure logging (I-08)** is treated in the write-up mostly as a falsification condition to check later; I would treat it as a blocking question to resolve *before* writing the 80-line implementation, since I found external (if indirect) evidence suggesting it may not hold as assumed, and the acceptance criterion for I-08's own live-verification step depends on it.
- **The exact-argument fragility of `intent_hash` aliasing** (which I-01, I-04, and I-07 all build on or interact with) is worth naming as a single shared risk rather than three separate footnotes: every one of those three ideas' fixes or experiments implicitly assumes a resumed/re-minted tool call arrives with byte-identical arguments across models. I-07 is designed to test this directly, which is good, but I-01's fix should be understood as making the *consequences* of that fragility worse in one direction (fewer false BLOCKs) while not touching the fragility itself — a genuine cross-model argument mismatch would still produce a silent duplicate after I-01 ships, exactly as before.
