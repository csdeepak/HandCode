# Phase 0 — Existing-system reconnaissance

## 1. Executive answer
Two of the five "hard problems" are already substantially solved by the tools you plan to sit beside, and building them from scratch would be waste. **Prompt-cache affinity already exists in LiteLLM** as `PromptCachingDeploymentCheck` (enabled via `optional_pre_call_checks: ["prompt_caching"]`), so your cache-intelligence component should CONFIGURE-and-extend, not BUILD — but it ships with a hardcoded 5‑minute affinity TTL (`ttl=300` with "no router setting that overrides this," per issue #28427) and a documented extended-prefix routing bug where, on a growing multi-turn prefix, "every request [routes] to a different deployment, completely defeating the purpose of prompt caching" (#19755) — which is exactly the gap worth owning. **Mid-tool-call double-execution is real and confirmed in OpenHands source**: the V1 SDK persists the `ActionEvent` to the append-only event log *before* the tool executor runs, and on resume `get_unmatched_actions()` re-drives those pending actions through the real tool executor — so a crash between action-persistence and observation-emit re-executes the side effect, and idempotency is left to the tool. That single fact validates your "session/turn journal + durable execution" thesis and means your control plane must own an idempotency/dedup layer. LiteLLM gives you rich pre/post-call hooks (`CustomLogger`), a spend-log schema, and Prometheus metrics, so the cost ledger and policy enforcement can be a plugin rather than a fork. The two components with the weakest existing coverage — and therefore the clearest BUILD verdicts — are the **capability matrix / cross-model-drift** tooling and a **policy compiler** that encodes explicit constraints and provider ToS.

## 3. INFERRED

**I1. Switching provider endpoints mid-session discards the warm cache, and LiteLLM cannot currently protect you across drift in the cacheable prefix.** Evidence: `PromptCachingCache` keys on a sha256 of the *entire* serialized message list (V6); condensation and any mid-prefix edit change the hash. Issue #16522 confirms "the whole message is put into cache rather than the part of cache_control." The extended-prefix fallback only "removes up to the last 3 messages and tries again" (#12584), and #19755 documents that with a growing multi-turn prefix, "every request [routes] to a different deployment, completely defeating the purpose of prompt caching" (Turn 1→Account A, Turn 2→B, Turn 3→C = "Zero cache utilization across conversation"). Inference chain: long agent contexts (a) are exactly where cache affinity matters most and (b) mutate their prefix via condensers and multi-message turns, so the existing affinity check degrades precisely under your workload. Confirm/falsify: run two deployments of one Claude model behind LiteLLM with `["prompt_caching"]`, drive a >5-minute agent loop with condensation, and inspect `cache_read_input_tokens` and served `model_id` per turn.

**I2. Your control plane must own an idempotency key per side-effecting tool call, because neither tool does.** Evidence: V1+V2 show OpenHands re-executes unmatched actions on resume, and the source note is explicit that "Tool-level idempotency is the tool's responsibility." LiteLLM operates below the tool boundary and never sees tool execution. Inference chain: since the action is durably logged *before* execution and replayed after a crash, the only place to dedup a side effect that already happened is a layer that records tool-call completion out-of-band (your journal), keyed by `tool_call_id`. Confirm/falsify: kill the OpenHands process between an action append and its observation, resume, and observe the tool running twice (Exercise, Part A).

**I3. Cross-model drift is not addressed by either tool and is inherent to the "endpoint can change" principle.** Evidence: LiteLLM routes by latency/cost/usage/cache — none consider whether model B produces the same *plan* as model A from identical state (V8). OpenHands stores state model-agnostically, but on resume its `Agent` validation requires only that *tools* match; the LLM can be freely changed. Inference chain: identical durable state + different model = different next `ActionEvent`, and nothing measures or gates this. Confirm/falsify: fork a conversation (`LocalConversation.fork`) at a fixed event and `run()` under two different models; diff the resulting action sequences.

**I4. The cost ledger can be assembled from existing telemetry, but no existing component ties spend to a logical work unit.** Evidence: LiteLLM `LiteLLM_SpendLogs.session_id` (from `x-litellm-trace-id`) and OpenHands `conversation.state.stats.accumulated_cost` both exist (V10, V5). Inference chain: if OpenHands sets a stable trace-id per conversation/turn and forwards it, LiteLLM spend rows become joinable to journal turns — but that wiring is not out-of-the-box. Confirm/falsify: check whether OpenHands forwards `x-litellm-trace-id`/`session_id` by default (see U2).

## 5. Mechanism explanation

**OpenHands as an event-sourced state machine.** The mental model: a stateless `Agent` is effectively a pure function `step(state) -> events`, and all mutability lives in one `ConversationState`. The `EventLog` is append-only; each event is a Pydantic model serialized to its own JSON file (`event-00000-<id>.json`) alongside `base_state.json`. Reconstruction on load replays those files to rebuild the in-memory `view`. Because the log is the source of truth, "resume" is just "load `base_state.json` + events, recompute the active branch, keep stepping." The append site (`ConversationState.append_event`) is the single chokepoint that stamps lineage (`parent_id`) and advances HEAD — this is what makes forks/branches (`fork`, `navigate_to`) coherent, and it is where the `_default_callback` in `LocalConversation` persists every event under the state lock.

The **critical failure mode** is the ordering within one step. Inside `_handle_tool_calls`, the sequence is: (1) build `ActionEvent`; (2) `on_event(action_event)` → append to log (durable); (3) later, `_execute_actions` → `_ActionBatch.prepare` runs the tool via `executor.execute_batch`, then `_ActionBatch.emit` appends the `ObservationEvent`. This "write-ahead intent" ordering is deliberate and good for observability and confirmation mode — you can pause with the action already durable (status `WAITING_FOR_CONFIRMATION`) and await human approval. But it means the log can contain an `ActionEvent` with no matching `ObservationEvent` at the instant of a crash. On restart, `step()` calls `get_unmatched_actions()`, finds that orphan, and *executes it* — through the real executor, not the model. If the original process had already run `rm -rf`, sent the email, or POSTed the payment before dying, resume runs it again. The data structure that makes the orphan *detectable* is the `(action_id, tool_call_id)` pairing in `get_unmatched_actions`; the data structure that is *missing* is any record that "tool_call_id X already produced a real-world effect." That is the hole your journal + idempotency layer fills: record a durable "tool committed" marker keyed by `tool_call_id` before the side effect, and on resume convert an unmatched-but-already-committed action into a synthesized observation instead of a re-execution.

**LiteLLM as a routing/failover data plane.** The `Router` holds a `model_list` of deployments grouped by `model_name`. A request enters, optional pre-call checks narrow the candidate deployment set, then the routing strategy picks one. `simple-shuffle` (default) weights by rpm/tpm; `least-busy` tracks in-flight counts; `latency-based` tracks response times; `usage-based-v2` and `cost-based` keep per-minute counters in Redis and pick the lowest. Failover is layered: `num_retries` within a deployment, then `fallbacks`/`context_window_fallbacks`/`content_policy_fallbacks` to other model groups, with `order` levels tried in sequence. A deployment that exceeds `allowed_fails` within the 1‑minute `failed_calls` window is written into the `CooldownCache` for `cooldown_time` seconds and skipped until it expires (shared across workers via Redis/DualCache).

The **prompt-cache-affinity mechanism** is a pre-call check, not a strategy, so it composes with any strategy. `PromptCachingCache` computes `sha256(serialize(messages)+serialize(tools))` → `deployment:{hash}:prompt_caching`. On a cache *write* it stores the chosen `model_id` under that key with `ttl=300`. On the next request it looks up the full-message key, then `messages[:-1]`, `[:-2]`, `[:-3]`, and if any hits, forces routing to the stored `model_id` so the warm provider-side cache is reused. The **three structural weaknesses** for your workload: (a) the 300s TTL is hardcoded and cannot match a 1‑hour ephemeral cache (#28427); (b) the slice search only walks back 3 messages, so an agent turn that appends more than 3 messages (tool result + assistant + …) past the cached prefix misses affinity and re-routes (#12584/#19755); (c) the key hashes the *whole* message list rather than only the `cache_control`-marked prefix (#16522), so any downstream mutation invalidates it. These are precisely the conditions long agent loops with condensers create — which is why "cache intelligence" is a real component even though a v1 exists. (Note the newer `deployment_affinity` check may address (a)/(b) by pinning `model_info.id` with a configurable TTL — see U4.)

**How the two planes meet for your control plane.** Telemetry flows out of LiteLLM three ways: synchronous response headers (`x-litellm-response-cost` and components), durable `LiteLLM_SpendLogs` rows (with `session_id`/`request_tags`), and Prometheus counters. Control flows in two ways: config (`model_list`, `router_settings`) and `CustomLogger` hooks — `async_pre_call_hook` can rewrite or reject a request *before* spend, and `async_post_call_success_hook` can annotate the response. This seam lets your policy compiler and cost ledger be a plugin: compile policy to a hook that inspects `data` (model, messages, metadata, key) and either mutates routing or raises to block. OpenHands, meanwhile, emits per-request metrics (tokens, cost, latency, cache read/write tokens) into `conversation.state.stats`, and its events are your ready-made session/turn journal — provided you bridge a stable trace-id across the two planes (U2).

## 7. Hands-on exercise (~90 minutes)

**Goal: prove the double-execution failure and the cache-affinity gap in one sitting.**

**Part A — double-execution (45 min).** Install the OpenHands SDK. Write a trivial custom tool whose executor appends a line to `/tmp/side_effect.log` and then `time.sleep(3)`. Start a `LocalConversation` with `persistence_dir` set, send a message that forces exactly one call to that tool, and `conversation.run()` in a thread. During the 3-second sleep (after the `ActionEvent` is written but before the `ObservationEvent`), `kill -9` the process. Restart with `LocalConversation(agent=None, persistence_dir=..., conversation_id=...)` and `run()`. **Observe:** the line count in `/tmp/side_effect.log`, and the `events/` directory for an orphaned `ActionEvent` with no sibling `ObservationEvent`. **Surprising if:** the line appears twice (confirms resume re-executed the unmatched action, per V1/V2) — or *once*, which would mean a dedup you didn't expect exists (resolves U1).

**Part B — cache affinity (45 min).** Run the LiteLLM proxy with two deployments of the same Claude model (two keys/accounts, same `model_name`) and `router_settings: optional_pre_call_checks: ["prompt_caching"]`. Point OpenHands at the proxy (`base_url`). Run an agent loop long enough to trigger the default condenser, and read `cache_read_input_tokens`/`cache_creation_input_tokens` per turn (response headers or spend logs) plus the served `model_id`. **Observe:** whether `model_id` stays pinned and cache reads persist across turns. **Surprising if:** affinity holds *through* a condensation event (it likely won't — the prefix hash changes, per #16522/I1), or if it silently breaks after >5 minutes idle (the hardcoded 300s TTL, V7). Either outcome quantifies the exact BUILD scope for cache intelligence.
